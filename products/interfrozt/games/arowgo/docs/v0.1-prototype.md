# AROWGO v0.1 prototype

This is the current implementation contract. Earlier first-playable reports and the imported masterplan describe historical evidence or future ambition; they do not override this release scope.

## Player journey

Home → Play/Continue → puzzle → result → Next level → Worlds. Home, Worlds, Modes, Progress and Settings have a persistent five-tab bottom navigation. The puzzle deliberately has no bottom navigation. Its Home action returns to the hub without resetting the saved attempt. Hash routes support browser Back and reload: `#home`, `#worlds`, `#modes`, `#progress`, `#settings`, `#play/1` through `#play/5`. Locked or invalid routes show Home rather than opening locked content.

Worlds contains five Bloom Valley levels. A Story clear unlocks the next; Practice does not unlock or pay rewards. A finished level can be replayed from Worlds. Failed attempts restart when selected from Worlds. An unfinished attempt resumes. The last result returns to Worlds; Play again remains available on every result.

## Gameplay and content

The original rigid swept-body legality contract is unchanged: every cell in the arrow's shape must have an unobstructed exit in its head direction. Snake motion is presentation, not a replacement collision model. Blocked arrows ease toward contact and recoil; the board remains unchanged and Story loses one heart. Three mistakes end a Story run. Practice permits unlimited mistakes.

Levels are fixed, versioned JSON content under `content/levels`. Levels 2–5 were authored using a seeded offline placement search, then accepted only when a complete legal sequence existed. Runtime does not randomly generate boards. Level 2 is a deliberate shorter breather; density then increases. Every solution is checked by the domain validator and automated campaign tests. Human difficulty/playtesting remains a follow-up.

## Tools and motion

Hint chooses one currently legal arrow. A warm ring around its tip gently expands and contracts for up to five seconds, with a soft halo and brief board-edge glow. It does not move or remove the arrow. Selecting an arrow, Erase, reset or leaving the puzzle clears the hint. Reduced motion uses a static highlight. Repeated use restarts the cue. Erase selects an arrow, asks for confirmation, and wipes it away without spending hearts or coins. Both tools mark the attempt assisted and limit a Story clear to one star. Analyze is not exposed.

Success retains the existing staged stars, animated reward counter and encouraging copy. Failures protect earned progress and offer retry or Practice. No streak penalty, paid rescue, ad or purchasing loop is present. The thinking-related motto describes practice, not a clinically demonstrated cognitive improvement claim.

## Progress and persistence

Each level has a separate atomic session and last-valid backup. Level 1 retains `arowgo.slice.v1`, preserving existing first-playable saves. Later keys are `arowgo.level.bloom-02.v1` through `arowgo.level.bloom-05.v1`, with `.backup` companions. Each ledger contains the board, attempt, mode, mistakes, assisted/erased state, best stars and first-clear reward flag. Existing validation and recovery apply independently to each level.

The wallet shown across pages is the sum of these validated ledgers. Each first Story clear grants 25 coins; the maximum is 125. Best stars sum to 15. Replay cannot duplicate rewards. No cross-key wallet transaction is necessary. No server or account is used. Storage failure retains playable in-memory state and reports that persistence is unavailable in the puzzle. Browser data deletion loses local progress. Multiple simultaneous tabs are not synchronized.

## Layout and accessibility

Mobile gameplay uses the dynamic viewport height and safe-area insets. A ResizeObserver fits the square SVG board inside the available region. The HUD, tools and mode action stay visible; narrow landscape puts controls beside the board. Desktop gameplay also fits the viewport. Hub pages keep the bottom navigation visible; short landscape may scroll only the page's inner content. Settings dialogs scroll internally when necessary. No document-level scrolling is needed for the supported phone layouts.

Typography uses local Satoshi with responsive heading sizes. Essential actions use readable labels. Navigation uses links with `aria-current`; locked levels use disabled buttons. Puzzle arrows remain keyboard buttons. Settings dialogs trap focus and restore it. System reduced-motion always wins; manual reduced-motion and Rich/Subtle preferences persist and synchronize between the hub and puzzle in the current tab.

## Code map

- `src/ui/Prototype.tsx`: page router, five controllers, navigation, derived wallet and unlocks.
- `src/ui/App.tsx`: focused puzzle, results, tools, in-game settings and Rule lab.
- `src/domain/campaign.ts`: validated level catalog and names.
- `src/domain/rules.ts`: immutable legality and solver.
- `src/application/session.ts`: deterministic attempts and rewards.
- `src/storage/save.ts`: configurable per-level keys, validation and backup recovery.
- `src/game/Board.tsx`: vector rendering and motion.
- `src/ui/useMotion.ts`: persisted preferences and system preference integration.
- `src/ui/elements/Rewards.tsx`: reusable coins, hearts, counters and encouragement.

## Verification and release

Run `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm test:e2e`, then `pnpm android:sync` (web build and native asset sync). Tests cover rules, complete solutions, reward idempotency, isolated saves, progression, reload, tools, collision, reduced motion, small-screen bounds, result screens and real pointer interaction. Browser tests use desktop and phone emulation; physical-device and native Android compilation are separate pending checks.

Deployment uses the tested static Vite output with `node scripts/prepare-vercel.mjs`, then the linked Vercel project's prebuilt production deployment. See [deployment record](deployment-vercel.md) for exact release evidence. Screenshots are under `verification/v01-*`.

## Explicit prototype limits and next work

No purchases, backend, cloud save, social features, leaderboards, audio, push notifications, runtime level generation or additional worlds. Five levels constitute this v0.1 browser prototype, not the complete commercial masterplan. Next priorities: physical iOS/Android browser checks (safe areas, browser chrome and orientation), human difficulty sessions, content tuning, native SDK build, and shared multi-tab save arbitration before adding more progression systems.
